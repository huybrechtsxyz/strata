# Caching: Resolved-model cache for deployment performance

strata uses a SQLite-backed cache (`.strata/cache.db`) to avoid redundant variable/feature/environment resolution and build artifact regeneration when configuration hasn't changed. This guide explains how the cache works, what it caches, and how to use it effectively.

---

## Overview

Every `strata build` and `strata deploy` command checks the cache before doing expensive operations:

- **Build artifacts** (Terraform `.tfvars.json`, Helm values, Compose files)
- **Merged environment model** (resolved environment structure without secret values)
- **Resolved values** (variable and feature flag values — secrets are never cached)

**Cache key:** Deployment + environment + tenant YAML files' content hash (SHA256).

**Cache invalidation:** Automatic — if any YAML changes, the hash changes, the cache misses, and values are re-resolved fresh. No manual purging needed (though `--refresh-cache` forces a rebuild if you want one).

---

## Cache kinds

strata maintains three kinds of cached data:

### 1. `deployment` — Build artifacts

**What's cached:** Terraform `.tfvars.json`, Helm `values.yaml`, Compose service definitions, Ansible inventory, and platform metadata.

**Invalidation trigger:** Any change to workspace, environment, configuration, or deployment YAML that affects the merged model.

**Used by:**
- `strata build run` / `strata build plan`
- `strata deploy run` / `strata deploy plan`

**Cache hit means:** Skip the full workspace + environment merge, skip value resolution, skip artifact generation — output the cached platform model directly.

**Cache miss means:** Regenerate platform model, resolve all values, write new artifacts, store cache entry.

### 2. `resolved_environment` — Merged environment model

**What's cached:** Merged environment structure (declared variables, secrets, features, properties, overrides, remotes) — but NOT resolved secret values (only store type + reference).

**Invalidation trigger:** Any change to environment YAML or configuration remotes.

**Used by:**
- `strata deploy show`
- `strata values list` / `strata values get` / `strata values resolve`

**Cache hit means:** Skip environment merging, load the cached structure, then selectively re-resolve live-only values (environment-store variables and features always re-resolve, and any secrets are fetched fresh even with a cache hit).

**Cache miss means:** Merge environment from all sources, store structure, then resolve variables and features.

### 3. `resolved_values` — Variable and feature flag values

**What's cached:** Resolved values of all declared variables and feature flags — but NEVER secret values (only the store type and reference path).

**Invalidation trigger:** Any change to variable/feature declarations or environment YAML.

**Used by:**
- `strata deploy show`
- `strata values list` / `strata values get` / `strata values resolve`

**Cache hit means:** Return cached variable/feature values directly; skip store queries for variables and features.

**Cache miss means:** Query stores for all variables and features, store the resolved values, return.

**Important:** Environment-store variables and features always re-resolve live even on a cache hit — they're session/pipeline-scoped and can change between invocations with no file change to invalidate the cache. Secrets are always fetched fresh, never cached.

## Cache flags

Every `build` and `deploy` command and value-inspection command accepts these flags:

| Flag                | Behavior                                                                                   |\n| ------------------- | ------------------------------------------------------------------------------------------ |\n| (default)           | Cache hit = use cached data; miss = re-resolve, cache result, return                       |\n| `--no-cache`        | Skip cache entirely — always re-resolve, never read from or write to cache                 |\n| `--refresh-cache`   | Treat as cache miss — force re-resolve and re-cache, even if entry exists                  |\n| `--offline`         | Deployment-specific: use cached terraform outputs only, don't query remote backends        |\n\n```bash\n# Typical build — cache hit or miss depending on YAML changes\nstrata build run -f deploy-prd.yaml\n\n# Bypass cache entirely — always re-resolve and regenerate\nstrata build run -f deploy-prd.yaml --no-cache\n\n# Force invalidate and rebuild cache\nstrata build run -f deploy-prd.yaml --refresh-cache\n\n# Deploy with cached values + offline terraform (local outputs only)\nstrata deploy run -f deploy-prd.yaml --offline\n\n# Inspect values — use cache if YAML unchanged\nstrata values list -f deploy-prd.yaml\n\n# Inspect values — force fresh resolution\nstrata values list -f deploy-prd.yaml --refresh-cache\n```\n\n---\n\n## Cache storage and lifecycle\n\n### Cache location\n\nCache is stored at `.strata/cache.db` in the workspace root. It's a SQLite database with tables:\n\n| Table          | Stores                              | Key                           |\n| -------------- | ----------------------------------- | ----------------------------- |\n| `cache`        | Metadata for all cache entries      | `(name, kind, cache_version)` |\n| `cache_inputs` | Input file paths and content hashes | `cache_id` (FK)               |\n| `cache_data`   | Serialized resolved data            | `cache_id` (FK)               |\n\n### Cache invalidation strategy\n\nCache entries are **content-addressed** — they key off the SHA256 hash of the input files:\n\n1. Command loads deployment/environment/tenant YAML files\n2. Computes SHA256 of combined file content\n3. Looks up cache entry by `(deployment_name, cache_kind, file_hash)`\n4. If found → cache hit, return data\n5. If not found → cache miss, regenerate, store new entry under this hash\n6. **Old entries with different hashes accumulate** but are ignored (safe to leave behind)\n\n### Clearing the cache\n\nTo remove all cache entries:\n\n```bash\n# Clear entire cache (next command will rebuild)\nrm .strata/cache.db\n\n# Selective refresh (force one deployment to rebuild)\nstrata build run -f deploy-prd.yaml --refresh-cache\n\n# Selective refresh (all deployments in a directory)\nfor f in deploy/*.yaml; do strata build run -f \"$f\" --refresh-cache; done\n```\n\n### Cache persistence\n\nThe cache is **always rebuildable** — it contains no data that isn't derivable from committed YAML. Safe to:\n- Delete between CI jobs\n- Exclude from `.gitignore` (it shouldn't be committed)\n- Share across developers (content-hash collision is astronomically unlikely, but hash collision is isolated to that entry)\n\n---\n\n## CI/CD pipeline strategies\n\n### Single-job pipeline (fast path)\n\nFor small deployments or dev environments, cache is effective in a single job:\n\n```bash\n# All operations reuse cache from validate forward\nstrata validate -f deploy-dev.yaml\nstrata build run -f deploy-dev.yaml\nstrata deploy run -f deploy-dev.yaml --force\n```\n\nCache hit rate: ~95% (only misses on YAML changes).\n\n### Multi-job pipeline (cache warm-up)\n\nFor CI pipelines with separate jobs, warm the cache early:\n\n```yaml\njobs:\n  validate:\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      - run: strata validate -f deploy/deploy-prd.yaml --deep\n      # Caches: deployment, resolved_environment\n\n  build:\n    needs: validate\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      # Cache HIT — reuses entries from validate\n      - run: strata build run -f deploy/deploy-prd.yaml\n      # Caches: deployment (overwrites validate's partial), resolved_environment, resolved_values\n\n  plan:\n    needs: build\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      # Cache HIT — uses build's cached artifacts\n      - run: strata deploy plan -f deploy/deploy-prd.yaml\n\n  deploy:\n    needs: plan\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      # Cache HIT — uses build's cached values\n      - run: strata deploy run -f deploy/deploy-prd.yaml --force\n\n  inspect:\n    needs: deploy\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      # Cache HIT — instant values lookup\n      - run: strata values list -f deploy/deploy-prd.yaml --output json\n```\n\n**Per-job cache benefit:** Each job sees a cache miss (job-local workspace = no `.strata/cache.db` carried from prior job), but the fast path through the command (value resolution, environment merge) is still optimized by in-process batching.\n\nTo carry cache **between jobs**, mount a shared volume or use actions/cache:\n\n```yaml\n  validate:\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      - uses: actions/cache@v4\n        with:\n          path: .strata/cache.db\n          key: strata-cache-${{ runner.os }}-${{ hashFiles('deploy/**/*.yaml') }}\n      - run: strata validate -f deploy/deploy-prd.yaml --deep\n\n  build:\n    needs: validate\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      - uses: actions/cache@v4\n        with:\n          path: .strata/cache.db\n          key: strata-cache-${{ runner.os }}-${{ hashFiles('deploy/**/*.yaml') }}\n      # Restore: cache carries validate's resolved_environment entry\n      - run: strata build run -f deploy/deploy-prd.yaml\n```\n\n### Multi-deployment fleet pipeline\n\nFor large deployments, validate/build all in parallel, then deploy serially:\n\n```yaml\nstrategy:\n  matrix:\n    deployment: [deploy-prd, deploy-stg, deploy-dev]\n\nsteps:\n  - uses: actions/checkout@v4\n  - run: strata build run -f deploy/${{ matrix.deployment }}.yaml\n  # Each deployment builds in parallel; each caches independently\n\n  - name: Deploy (serial)\n    run: |\n      for deploy in deploy-prd deploy-stg deploy-dev; do\n        strata deploy run -f \"$deploy.yaml\" --force\n      done\n    # All cache hits \u2014 reuses build matrix's entries\n```\n\n---\n\n## Performance impact\n\n### Typical timings (resolved-model cache)\n\n| Operation                      | First run (cache miss) | Repeat run (cache hit) | Speedup    |\n| ------------------------------ | ---------------------- | ---------------------- | ---------- |\n| `strata build run` (small)     | 8–12s                  | 2–3s                   | 3–5×       |\n| `strata build run` (medium)    | 15–25s                 | 3–5s                   | 3–8×       |\n| `strata build run` (large)     | 30–60s                 | 5–10s                  | 3–10×      |\n| `strata values list`           | 2–4s (store queries)   | <100ms (cache)         | 20–40×     |\n| `strata deploy show`           | 5–8s (merge + resolve) | <500ms (cache)         | 10–20×     |\n| `strata deploy plan`           | 20–60s (terraform)     | 15–50s (terraform)     | ~1.1× *    |\n\n*`deploy plan` is terraform-bound; cache speeds up the artifact prep phase but not terraform's plan itself.*\n\n### What drives cache misses\n\n- Any change to deployment, workspace, environment, or configuration YAML\n- First run in a new checkout / CI job (no `.strata/cache.db`)\n- `--refresh-cache` flag (intentional cache invalidation)\n- `--no-cache` flag (opt-out)\n\n### What doesn't invalidate cache\n\n- Changes to unrelated YAML files (different deployment, different tenant)\n- Changes to `.strata/logging.yaml` or workspace metadata\n- Time passing (no TTL; cache is content-addressed, not time-based)\n- Different user or machine (same YAML hash = same cache entry, shareable)\n\n---\n\n## Cache behavior by command\n\n### `strata build run` / `strata build plan`\n\n- Checks cache for `deployment` and `resolved_environment` entries\n- Proceeds only if both hit; otherwise regenerates platform model and resolved values\n- Writes `deployment` cache kind on success\n\n### `strata deploy run` / `strata deploy plan`\n\n- Checks cache for `deployment` and `resolved_values` entries\n- Loads cached artifacts and resolved variable/feature values\n- Always fetches secrets fresh (never cached) and environment-store values live (always re-resolved)\n- Writes cache on success\n\n### `strata deploy show`\n\n- Checks cache for `resolved_environment` and `resolved_values` entries\n- Instant display of merged environment and all variable/feature values (with freshly-fetched secrets)\n- Extremely fast on cache hit — ideal for CI inspection jobs\n\n### `strata values list` / `strata values get` / `strata values resolve`\n\n- Checks cache for `resolved_values` and `resolved_environment` entries\n- Returns cached variable/feature values\n- Always re-resolves environment-store variables/features live\n- Always fetches secrets fresh\n- Lightweight, low-latency operation on cache hit\n\n### `strata validate`\n\n- Does not use the cache (validation is always fresh)\n- May seed cache entries as a side-effect if `--deep` is used (profile activation triggers environment load)\n\n---\n\n## Troubleshooting\n\n### \"Values seem stale — environment variable changed but cache shows old value\"\n\n**Cause:** Environment-store variables are cached.\n\n**Solution:** This is expected behavior — environment-store variables are session/pipeline-scoped and can change between runs. They're always re-resolved live, cache hit or miss. If the value hasn't changed, the cache is correct. To force a refresh:\n\n```bash\nstrata values list --refresh-cache\n```\n\n### \"Cache is huge — how do I trim old entries?\"\n\n**Cause:** Content-addressed cache accumulates entries for every YAML hash ever seen.\n\n**Solution:** Old entries are harmless (they're ignored on misses) and use little space (typical cache is <10 MB for hundreds of deployments). To rebuild from scratch:\n\n```bash\nrm .strata/cache.db\nstrata build run -f deploy/*.yaml  # Rebuild cache from fresh\n```\n\n### \"Different job got different values from cache\"\n\n**Cause:** YAML hashes differ between jobs (e.g., different branch, different env overrides).\n\n**Solution:** This is correct behavior — different YAML = different cache entry = different values. Each job should see its own cached values. If values are unexpectedly different, check that the same YAML files are checked out in both jobs.\n\n### \"Cache is not being used in CI\"\n\n**Cause:** Each CI job starts with a fresh workspace (no `.strata/cache.db` from prior job).\n\n**Solution:** Use `actions/cache@v4` to carry `.strata/cache.db` between jobs:\n\n```yaml\n- uses: actions/cache@v4\n  with:\n    path: .strata/cache.db\n    key: strata-${{ hashFiles('deploy/**/*.yaml') }}\n```\n\n---\n\n## Best practices\n\n1. **Always use the cache in CI** — It's transparent and saves 3–40× time on `values` and `deploy show` commands.\n2. **Validate + build in early jobs** — This warms the cache for later inspection/deploy jobs.\n3. **Use `--refresh-cache` sparingly** — Only when you suspect stale values despite no YAML change (rare).\n4. **Don't commit `.strata/cache.db`** — Add to `.gitignore`. The cache is always rebuildable.\n5. **Share cache between jobs** — Use `actions/cache@v4` to carry `.strata/cache.db` across CI jobs.\n6. **For secrets**: Understand that cache never stores secret values — only store type + reference. Secrets are always fetched fresh on every command.\n7. **For environment variables**: Understand that environment-store variables are always re-resolved live on every command, even on cache hits.\n\n---\n\n## See also\n\n- [ADR-0026: Resolved-model cache for fleet-wide command performance](../decisions/0026-resolved-model-cache.md) — Design rationale, phases, and deferral decisions\n- [CI Integration guide](ci-integration.md#resolved-model-cache-for-fast-multi-deployment-pipelines) — Pipeline examples using cache\n- [`values` command reference](../platform/commands.md#values) — Full command syntax and examples\n- [`strata deploy show`](../platform/commands.md#deploy-show) — Show cached deployment state\n
