## Findings

1. **`deploy_log_path` is pure local filesystem path resolution.** `ConfigurationService.get_deploy_log_path` has no remote transport (no S3/Blob/GCS backend), unlike locks (ADR-0007) or work items (ADR-0057). Confirmed: making it cross-machine-safe requires pointing it at an operator-provided shared/mounted path — strata itself does nothing remote here.
2. **New finding — gitops manifest push is already genuinely remote.** `ConfigurationManifestModel` supports `manifest: { type: gitops, repository, branch, push_manifest: true }`. After every deploy, `push_to_remote()` performs a real git commit+push of the deployment manifest (carrying `spec.status: success|partial|failed`) to a remote repository. This requires no shared filesystem — it's remote via git today. **Gap:** there is no matching `pull_from_remote()` — a downstream consumer must `git pull` the state-repo itself before reading it.
3. **Correction to earlier session log and decisions.md entry:** `strata deploy status` does **not exist** as a registered command — this was a naming error carried over from stale docs/skills (`SKILL.md` files under `.squad/skills/` still reference it). The actual live-Terraform-state-query command is `strata env status -f <file>` (`StatusEnvCommand`), which runs `terraform init` + `terraform show -json` against the upstream's real remote Terraform backend — inherently cross-machine, since that's the entire point of a remote backend. Only `deploy lock status` exists under the `deploy` group.
4. **Ranked recommendation for cross-machine dependency checking (best → worst):**
   1. `strata env status -f <upstream>` — queries the live Terraform backend directly, no shared storage needed.
   2. Deployment manifest with `type: gitops` + `push_manifest: true` — genuinely remote via git, matches the earlier-proposed `spec.requires` design well, but needs an explicit `git pull` step downstream.
   3. Shared `deploy_log_path` on a mounted network share — works, but has zero strata-side remote mechanics; all correctness is on the operator.
   4. Webhook/ndjson audit sinks — not usable standalone today, no query-side API.

## Correction Applied

This updates/corrects the earlier flagged open finding (`danny-cross-deployment-dependency-gap`, already merged into `decisions.md`): the recommended backing store for the future `spec.requires` field should now specifically call out the gitops-manifest mechanism (already implemented) as the preferred remote signal — not "the manifest" generically — with `env status` as a live-state fallback check.
