## Routing

- **Agent routed:** Danny (Lead/Architect)
- **Why:** A partner team asked whether strata can gate a lower deployment layer (e.g. zone) on an upper layer (e.g. landscape) being successfully deployed first, across a layered hierarchy of separate `kind: deployment` files (tenant/landscape/zone/zone-tenant/zone-tenant-environment). Assessing whether an existing or new architectural mechanism covers cross-deployment-file dependencies is Danny's remit.
- **Mode:** background — pure discussion/assessment session, no code changes expected.

## Task

Determine whether strata has a built-in mechanism to gate one `kind: deployment` file's execution on another, separate deployment file having already succeeded, and propose a direction if not.

## Input Artifacts

- Intra-file `stages[].depends_on` (existing stage-dependency mechanism, scoped to a single deployment file)
- `docs/guides/at-scale.md` — drafted but unimplemented `spec.inputs.from` concept
- `docs/decisions/0057-deployment-workflow-orchestration.md` and `docs/decisions/0032-approval-workflows-and-gates.md` (ADR-0057 gate framework)

## Files Produced

- None — no code or docs changes. Findings recorded via Scribe session log and this orchestration entry.

## Outcome

- **Confirmed:** No built-in mechanism exists today for cross-deployment-file dependency gating. `stages[].depends_on` only operates within a single deployment file. The `spec.inputs.from` concept sketched in `docs/guides/at-scale.md` is unimplemented.
- **Initial proposal:** Extend ADR-0057's gate framework with a new `type: dependency` gate.
- **Revised after Linus's pushback:** Agreed ADR-0057 gates are environment-scoped and built for human decisions (approvals, WorkItems, exit code 5) — a poor fit for a binary, disk-checkable precondition with no human in the loop. Concurred with routing this as a new `spec.requires` field instead (Linus's Approach 1).
- **Status:** Discussion only — no direction implemented. Flagged as an open finding for a future session.
